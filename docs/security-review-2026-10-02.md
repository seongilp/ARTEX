# ARTEX 백도어 및 보안 점검 — 2026-10-02

## 결론

현재 작업 트리의 직접 작성된 코드와 주요 실행 경로에서 **숨겨진 관리자 암호, 별도 비밀 원격 제어 서버, 작성자에게 비밀을 몰래 보내는 고정 목적지 등 의도적인 백도어의 증거는 발견하지 못했다.** 이는 백도어 부재를 보증하는 결과가 아니다. 공식 배포 바이너리/컨테이너와 모든 전이 의존성의 소스를 전수 분석하거나 실제 대상 테스트 중의 네트워크를 관찰한 것은 아니다.

실제로 재현한 작업 공간 경계 우회와 초기 설정·인증·명령 실행·공급망의 위험이 있다. 특히 이 프로그램은 AI가 실제 셸 명령을 실행하도록 설계되어 있어, 백도어가 없어도 개인 개발 머신과 비밀이 있는 환경에서 그대로 실행하는 것은 위험하다.

요청에 따라 이번 변경은 한국어 번역과 그 호환성 수정이다. 아래 보안 문제는 점검 결과이며, 인증 정책이나 배포 설정을 임의로 바꾸지 않았다.

## 범위 및 방법

- 로컬 작업 트리 기준. 점검 시작 전부터 144개 파일에 수정이 있었으며 이를 보존했다. upstream 원본 전체에 대한 판정이 아니다.
- 시작점·서버 라우팅·JWT 인증·비밀번호 설정·파일 API·에이전트 명령·Python 사용자 도구·MCP·알림·기록 프록시·업데이트·설치 스크립트·Docker·릴리스 워크플로·브라우저 소스를 검토했다.
- URL/네트워크 호출, 프로세스 실행, 인코딩/동적 실행, 셸 지속성·키 설치 같은 패턴을 검색하고 실제 호출 위치를 확인했다. 모든 소스 줄을 동일 깊이로 수동 검토한 것은 아니다.
- 핵심 의존성 `github.com/Autumn-27/norma@v0.4.3`의 셸 실행·환경 변수·LLM/검색 목적지·MCP 실행 경로도 확인했다.
- `go mod verify`, `govulncheck`, `npm audit`, 기존 테스트와 임시 로컬 재현 테스트를 사용했다. 임시 재현은 새로 만든 테스트 파일만 읽었으며 실제 비밀 파일에 접근하지 않았다.
- 실제 사이트에 대한 스캔/침투, LLM 호출, 알림 발송, 설치 스크립트 실행, 배포 및 업데이트 적용은 하지 않았다.

## 우선 처리할 항목

### SEC-01 · 높음 · 초기 설정을 선점하여 관리자 계정 생성 가능

**영향:** 비밀번호를 아직 설정하지 않은 인스턴스에 먼저 접근한 사람이 관리자 비밀번호와 토큰을 얻고 에이전트 실행 기능을 사용할 수 있다.

근거:

- `cmd/artex/main.go:55`: HTTP 기본 바인딩이 `:8787`이다.
- `docker-compose.yml:31`: `8787:8787`을 호스트 전체 인터페이스에 게시한다.
- `server/auth.go:97`: `/api/auth/*`는 일반 인증을 제외한다.
- `server/auth.go:128`: `authInit`은 기존 해시가 비었는지만 확인하고 요청의 비밀번호를 저장한 뒤 토큰을 반환한다. 설치 시 생성한 일회용 비밀이나 로컬 요청 제한은 없다.
- `server/server.go:3879`: CORS가 `*`이며 POST/Content-Type을 허용한다. 미인증 초기화 API의 교차 출처 접근도 제한하지 않는다.
- `db/settings.go:21`: 초기 설정 저장이 별도 조건 없는 upsert이다. 읽기와 쓰기가 분리되어 초기화 경합도 원자적으로 방지하지 않는다.

검증: 임시 `httptest`로 토큰 없는 외부 Origin의 `/api/auth/init` 요청이 핸들러까지 도달함을 확인했다. 정상 `/api/settings` 요청은 토큰 없이 401이었다. 실제 PostgreSQL에서 비밀번호 선점·동시 초기화는 재현하지 않았으며 위 DB 동작은 소스에 근거한다. 이미 초기화된 서버의 비밀번호를 이 API로 일반적으로 덮어쓸 수 있다는 뜻은 아니다. 브라우저의 로컬 네트워크 접근 정책도 환경별로 다르다.

권장: 최초 설정을 localhost 또는 콘솔 일회용 토큰으로 제한하고 DB에서 조건부 원자적 초기화를 사용한다. 기본 공개 바인딩 대신 명시적 공개 설정을 두고 CORS 출처도 제한한다.

### SEC-02 · 중간 · 심볼릭 링크로 작업 공간 바깥 파일 읽기 — 재현 확인

근거: `server/workspace.go:29`의 `wsResolve`는 문자열 경로 정규화와 접두사만 확인한다. `server/workspace.go:111`, `124`의 `os.Stat`/`os.ReadFile`은 심볼릭 링크를 따라간다.

재현: 임시 디렉터리에 `work/link.txt`를 만들고 그 부모의 `outside.txt`를 가리키게 했다. `wsRead`에 `path=link.txt`를 전달하자 작업 공간 밖 테스트 파일의 마커가 HTTP 200으로 반환됐다. 결과는 [local-probes.txt](security-review-2026-10-02/local-probes.txt)에 있다.

전제: 파일 API는 인증 뒤에 있으며 링크가 먼저 만들어져 있어야 한다. 미인증 원격 파일 읽기 취약점으로 분류하지 않는다. 에이전트는 이미 프로세스 권한으로 파일을 다룰 수 있으므로 새로운 OS 권한 획득도 아니다. 다만 작업 공간 경계 및 JWT 키를 작업 공간 바깥으로 옮긴 보호 의도를 무력화한다.

권장: 읽기·쓰기·다운로드·업로드 등 전 경로에 OS 수준의 루트 제한 파일 연산을 사용한다. 단순히 `EvalSymlinks` 후 다시 여는 방식만 사용하면 경합 문제가 남으므로 주의해야 한다.

### SEC-03 · 중간 · 비밀번호 정책·로그인 시도 제한·세션 폐기 미흡

- `server/auth.go:141`, `182`: 서버는 비밀번호가 비어 있는지만 확인한다. UI의 8자 제한을 API가 강제하지 않는다.
- `server/auth.go:208`: 로그인 시도 제한이나 지연 정책이 이 경로에 없다. 앱 외부 프록시의 제한은 확인하지 않았다.
- `server/auth.go:65`의 토큰은 7일 유효하며 `authChangePassword`는 암호 해시만 바꾼다. 기존 JWT를 무효화하지 않는다.
- `web/src/lib/auth.ts:20`: 토큰은 localStorage와 JavaScript가 읽을 수 있는 쿠키에 저장된다. 이는 XSS가 생겼을 때 탈취 범위를 키우는 요인이며, 이번 점검에서 XSS 공격 자체를 재현한 것은 아니다.

권장: 서버 비밀번호 정책, 로그인 제한, 비밀번호 변경 시 세션 버전/키 교체 등의 폐기 수단을 추가한다. 토큰 저장 방식을 바꿀 경우 CSRF 및 현재 SSE 인증 흐름까지 함께 검토한다.

### SEC-04 · 조건부 치명적 · npm 의존성의 알려진 취약점

현재 lockfile로 `npm audit --json`을 실행한 결과 **취약 패키지 항목 14개: critical 1, high 9, moderate 4**가 보고됐다. 이는 개별 CVE 14개 또는 실제 악용 가능한 경로 14개를 의미하지 않는다. 원본 결과는 [npm-audit.json](security-review-2026-10-02/npm-audit.json)에 저장했다.

`next` 16.2.9에 치명적 권고가 포함된다:

- Windows 파일시스템에서 Next 서버를 호스팅하는 경우의 RCE: [유지관리자 권고](https://github.com/vercel/next.js/security/advisories/GHSA-p293-qw3h-jr36).
- AVIF 이미지 최적화 API 관련 RCE: [유지관리자 권고](https://github.com/vercel/next.js/security/advisories/GHSA-2xp9-vwfh-vxw4).
- `next/og` ImageResponse 관련 RCE: [유지관리자 권고](https://github.com/vercel/next.js/security/advisories/GHSA-vcvr-r3jv-pc5j).

**배포 방식 구분:** `web/next.config.mjs`의 정적 export는 Node 서버 없이 Go가 정적 파일을 제공하며 이미지 최적화도 사용하지 않는다. 따라서 이러한 Next 서버 기능의 취약점을 정적 Go 배포에 그대로 적용해 ‘즉시 RCE 가능’이라고 결론 내릴 수 없다. Node의 `next dev`/`next start`, 이미지 처리 및 빌드 도구 환경은 별도 확인이 필요하다. 현재 앱에서 `next/og`의 사용은 확인하지 못했다.

권장: 수정 버전으로 의존성 및 lockfile을 갱신한 후 빌드·실행 검증과 재감사를 한다. 이번 작업에서는 요청하지 않은 대규모 의존성 업데이트를 적용하지 않았다.

## 의도된 기능이지만 위험한 신뢰 경계

### SEC-05 · 높음(운영 위험) · AI 명령은 호스트 권한으로 실행

`agent/worker.go:448`, `agent/chat.go:134`에서 SDK의 `permission.ModeBypass`를 사용한다. ARTEX의 `guard`가 별도로 개입하지만 `guard/guard.go:81` 이하에서 인터셉터가 없거나 도구가 제외되거나 일치 규칙과 예비 판정이 없으면 허용한다. 모든 명령이 무조건 허용된다는 뜻은 아니며, 이 계층은 OS 샌드박스가 아니다.

`norma/tool/bash.go:160`의 셸 실행은 `exec.CommandContext`, `server/customtool.go:398`의 Python 도구도 같은 프로세스 권한으로 실행한다. 사용자 도구는 `os.Environ()`도 상속한다. Dockerfile에는 별도 `USER` 지정이 없고 데이터·skills 경로가 쓰기 가능한 마운트다.

이는 공개된 제품 기능이며 자체로 숨겨진 백도어 증거가 아니다. 그러나 악성 대상 페이지의 프롬프트 주입, 잘못된 모델 판단, 악성 MCP/skill 또는 관리자 토큰 탈취가 로컬 파일·환경 비밀 접근으로 이어질 수 있다. 별도 VM/최소 권한 컨테이너, 전용 키, 필요한 디렉터리만 마운트, 네트워크 출구 제한으로 격리해야 한다. Docker 안의 root가 자동으로 호스트 root가 된다는 뜻은 아니다.

### SEC-06 · 중간(공급망 위험) · 다운로드한 코드와 업데이트 발행자를 신뢰

- `install.sh:22`: Docker 설치 스크립트를 받아 셸로 실행한다.
- `Dockerfile:22`, `33`: NodeSource 스크립트 실행 및 Playwright 관련 `@latest` 설치.
- `docker-compose.yml:18`: 기본 컨테이너 태그 `latest`.
- `selfupdate/github.go:15`, `25`: 고정 GitHub 저장소와 HTTPS 호스트 허용 목록을 사용하며 리다이렉트도 검사한다.
- `selfupdate/stage.go:66`, `90`: 같은 Release에서 받은 SHA256SUMS로 압축 파일을 검증한다. 독립된 서명 키로 발행자 서명을 검증하는 구조는 아니다.
- `selfupdate/stage.go:99`: 검증 후 새 바이너리의 `-h`를 실행한다. 해시 일치는 악성 동작 부재의 보장이 아니다.

숨겨진 다운로드 목적지는 확인되지 않았다. 정상적인 업데이트 기능이지만 upstream 계정이나 릴리스가 침해되면 바이너리와 해시를 함께 바꿀 수 있다. 검토한 소스로 직접 빌드하고 버전/이미지 digest/Action SHA를 고정하며 서명 검증을 추가하는 편이 낫다.

### SEC-07 · 정보 · 실제 외부 통신 및 TLS 예외

| 경로 | 확인한 용도 | 조건 |
| --- | --- | --- |
| OpenAI / Anthropic 및 사용자 LLM Base URL | 프롬프트, 도구 결과 전송 | 모델 호출 시. 기본 경로와 사용자 지정 주소를 모두 확인해야 함 |

| 사용자가 지정한 MCP / ScopeSentry | 도구 실행 및 자산 동기화 | 설정된 서버 연결 시 |
| DingTalk / Feishu / WeCom / Telegram / SMTP / webhook | 취약점 알림 | 사용자가 설정한 채널로 발송. 중국 서비스 URL의 존재 자체는 백도어 증거가 아님 |

`traffic/traffic.go:206`의 MITM 프록시는 대상의 TLS 검증을 생략하고, `enrich/enrich.go:96`도 자산 정보 수집에서 TLS 검증을 생략한다. `mcphttp/client.go:105`는 사용자가 insecure를 선택할 때만 검증을 생략한다. 업데이트 HTTP 클라이언트는 별도로 HTTPS 검증을 유지한다. 자체 서명된 테스트 대상을 지원하기 위한 동작과 업데이트 신뢰 경로를 구분했다.

확인한 앱 코드에서 별도의 고정 C2/광고·채굴 페이로드, 숨겨진 SSH 키 등록, cron/LaunchAgent 지속성 설치는 발견하지 못했다. Next.js 등 의존 라이브러리의 일반 telemetry와 전체 전이 소스는 별도 범위이며, 이번 빌드에서는 Next telemetry를 껐다.
